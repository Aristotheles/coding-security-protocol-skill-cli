# SECURITY_AGENT.md — Coding Security Protocol

This file contains mandatory security invariants for every human or AI agent working in this repository.

These rules are deliberately conservative.

Security decisions must be based on evidence, not model confidence.

---

# 1. Foundational Principle

**AI is not the source of security decisions.**

AI is:

- an interpreter of security evidence;
- a remediation assistant;
- a reviewer;
- optionally a runtime test operator.

Deterministic tools and explicit policy decide whether a change may proceed.

---

# 2. Decision Chain

The required security chain is:

**Evidence → Memory → Deduplication → Risk → AI Remediation → Deterministic Verification → Policy → Human Authority**

No layer may silently skip the next required layer.

---

# 3. Four Required Evidence Classes

Before a security remediation may pass the policy gate, evaluate:

```text
static_scan
tests
security_rescan
runtime_verify
```

States:

```text
PASS
FAIL
WAIVED
NOT_APPLICABLE
```

Missing evidence is not PASS.

Tool failure is not PASS.

No finding in a failed scanner run is not proof that the issue is gone.

---

# 4. Runtime Verification

Runtime verification occurs before policy evaluation.

Required order:

```text
AI/human patch
→ tests
→ relevant security rescan
→ runtime/browser verification
→ policy gate
→ merge/release
```

A runtime verification failure must reach the policy gate as failing evidence.

---

# 5. Runtime Waiver

`runtime_verify` may be waived only by a human.

A valid waiver records:

```text
approved_by
approved_at
reason
```

A waiver must not be generated by an AI agent.

A waiver must be auditable.

---

# 6. Finding Closure

AI may never mark a finding `CLOSED`.

A finding may close only after:

- relevant fix exists;
- tests meet project requirements;
- relevant scanner is re-run successfully;
- finding is absent or deterministically resolved;
- runtime verification is satisfied when applicable;
- security policy permits closure;
- secret rotation requirements are satisfied where applicable.

---

# 7. Finding Identity & Regression

Each finding has a permanent SEC ID.

Stable fingerprinting is used for deduplication and regression detection.

If the same closed vulnerability returns:

```text
reuse existing SEC ID
status = REOPENED
regression = true
```

Never hide regression by creating a fresh ID.

---

# 8. Source of Truth

Canonical finding state lives in:

```text
.security/findings/*.json
```

SQLite is an index.

If records disagree:

```text
canonical JSON wins
```

The index must be rebuildable.

---

# 9. Policy Authority

`security-policy.yml` is human-editable and machine-enforced.

AI may not:

- weaken policy;
- delete policy;
- change severity to pass a gate;
- add an exception for its own patch;
- change escalation timing;
- edit protected policy paths during remediation.

Policy changes require an explicit human task.

---

# 10. Policy Set

The MVP policy IDs are:

```text
POL-001
POL-002
POL-003
POL-004
POL-005
POL-006
POL-007
```

Their meaning is defined in `MVP.md` and `.security/policies/security-policy.yml`.

Do not reinterpret them through free-form model reasoning.

---

# 11. Critical Release Rule

If an open `CRITICAL` finding is covered by POL-001:

```text
release = BLOCK
```

No AI confidence score may override this.

---

# 12. AI Patch Verification Rule

If an AI patch fails to close the relevant finding on rescan:

```text
merge = BLOCK
```

Do not accept:

- "likely fixed";
- "scanner may be wrong";
- "code looks safe";
- "both AIs agree".

The deterministic result controls.

---

# 13. Dependency Rule

A lockfile change plus a new dependency requires human review.

Do not let an AI add a package as a convenience without triggering the appropriate review.

Prefer no new dependency when a safe built-in solution exists.

---

# 14. Coverage Rule

When coverage enforcement is configured, an AI security patch that reduces required coverage triggers policy.

Do not game coverage metrics by excluding newly changed security code.

---

# 15. Secret Rule

A hardcoded-secret finding is zero-tolerance for merge/release under POL-005.

Removing a secret from the current file is not sufficient remediation.

If a real secret was exposed:

```text
revoke/rotate
→ determine exposure
→ clean history if required
→ inspect misuse/logs
→ notify responsible owner
→ document incident
→ confirm rotation
```

Only after required remediation evidence exists may the finding close.

Never use a real credential in tests.

---

# 16. Secret Test Data

Security tests must use fake values clearly marked as non-production.

Example:

```text
TEST_ONLY_DO_NOT_USE
```

Do not generate realistic live API credentials.

---

# 17. Security-Critical Code

Changes in security-sensitive zones require human review according to policy.

Initial zones include:

```text
**/auth/**
**/middleware/**
**/permissions/**
**/session/**
**/crypto/**
```

Project configuration may extend these paths.

AI can propose a patch.
AI cannot provide the final human approval.

---

# 18. Stale Finding Escalation

For `HIGH` and `CRITICAL` findings in `OPEN` or `REOPENED` state:

```text
30 days → warning → security report
60 days → escalated warning → owner + responsible team
90 days → overdue → owner + responsible team + security lead
```

Do not treat dashboard visibility as notification.

Record notification delivery state.

Do not repeatedly resend the same stage without policy-defined retry behavior.

---

# 19. AI Provider Independence

No security control may require a named AI provider.

Codex, Claude Code, Antigravity and local models are replaceable.

If all AI providers fail:

```text
human_review
```

The scanner/finding/policy system continues to work.

---

# 20. AI Contract Validation

Free-text provider output is never trusted.

AI output must pass schema/contract validation.

Fallback or failure is required for:

- quota;
- timeout;
- malformed JSON;
- schema violation;
- missing finding ID;
- empty patch;
- invalid unified diff;
- patch dry-run failure;
- protected path violation;
- tool execution failure.

HTTP success does not imply security success.

---

# 21. AI Trust Profiles

Trust is assigned by capability profile.

Initial profiles:

```text
standard
restricted
```

A `restricted` provider patch always requires human review.

Do not infer trust from brand reputation.

Do not automatically upgrade trust because two AIs agree.

---

# 22. Reviewer Separation

When available, a patch should be reviewed by a provider different from the patch author.

Example:

```text
Codex patch
→ Claude review
```

If independent AI review is unavailable, use human review when policy/risk requires it.

AI review is advisory.

Tests/rescan/runtime/policy remain authoritative.

---

# 23. Protected Paths

AI remediation must not modify:

```text
SECURITY_AGENT.md
AGENTS.md
MVP.md
.security/policies/**
schemas/**
docs/ai-adapter-contract.md
security.config.yml
```

unless the human task explicitly authorizes editing that control surface.

A vulnerability patch touching a protected path is rejected by default.

---

# 24. Patch Boundary

AI patches should be constrained by:

```text
allowed_paths
forbidden_paths
max_files_changed
no_new_dependencies
```

Use the smallest patch that remediates the issue.

Do not permit repository-wide changes for a single finding without explicit human authorization.

---

# 25. Remote AI Data Minimization

Send remote AI providers only the minimum context needed.

Do not upload unrelated repository content.

Do not include:

- secrets;
- private keys;
- credentials;
- unrelated personal data;
- unrelated proprietary files.

If required evidence contains sensitive content, redact or use a safer review path.

---

# 26. Scanner Safety

Scanner commands must:

- use fixed executable + argv;
- not use shell interpolation;
- have a timeout;
- preserve raw evidence;
- record tool version when practical;
- record failed execution separately from findings.

Never execute scanner command text produced by an AI without validation.

---

# 27. SARIF Rule

SARIF is an interchange/evidence format, not the canonical finding store.

Normalize scanner output into stable finding records.

Do not assume two SARIF results are distinct vulnerabilities merely because tools emitted two results.

Deduplicate using the approved fingerprint process.

---

# 28. Fingerprint Rule

Fingerprinting must be stable and versioned.

It should derive from normalized security identity, not volatile fields such as:

- raw line number alone;
- scanner run ID;
- timestamps;
- transient message formatting.

A fingerprint algorithm change requires migration awareness.

---

# 29. Audit Rule

Security-relevant actions must be auditable.

Record when practical:

- finding opened;
- patch proposed;
- verification attempted;
- finding closed;
- finding reopened;
- accepted risk;
- escalation;
- gate decision;
- AI patch attempt;
- waiver;
- notification attempt.

Use UTC ISO-8601 timestamps.

---

# 30. Accepted Risk

`ACCEPTED_RISK` is a human security decision.

AI may recommend consideration but may not set accepted risk.

An accepted risk record should include:

- human approver;
- reason;
- timestamp;
- optional expiry/review date.

---

# 31. Fail-Closed Security

When security state is ambiguous:

```text
do not silently pass
```

Examples:

- policy parser failed;
- finding schema invalid;
- scanner crashed;
- rescan missing;
- test command missing;
- runtime evidence missing;
- DB update inconsistent;
- AI response invalid.

Return a non-zero state appropriate to the CLI contract.

---

# 32. No Security Theater

Do not add tools merely to increase scanner count.

MVP starts with:

```text
Semgrep
Trivy
```

Additional tools are added only when they cover a real gap.

Avoid duplicate noisy scanning that produces no decision value.

---

# 33. Tool Responsibilities

Initial responsibility boundaries:

```text
Semgrep
→ source security patterns / project rules

Trivy
→ dependencies / CVEs / secrets / container / IaC where enabled

CodeQL (later/optional)
→ deeper data-flow / taint analysis

MobSF (later/optional)
→ Android/mobile artifact analysis

OWASP ZAP (later/optional)
→ web/API runtime scanning
```

Do not treat overlapping findings as separate vulnerabilities automatically.

---

# 34. Human Authority

Human review is mandatory where policy requires it.

The security lead / reviewer can:

- approve policy changes;
- approve runtime waivers;
- accept risk;
- approve restricted-trust patches;
- review dependency additions;
- review auth/security-critical changes.

AI may assist but must not impersonate a human approver.

---

# 35. Security Gate Meaning

A PASS means:

- required evidence exists;
- required tools completed successfully;
- relevant policies did not block;
- required reviews are satisfied.

PASS does not mean "the software has no vulnerabilities."

Reports should preserve this distinction.

---

# 36. Current MVP Security Priority

The first proof of correctness is not AI remediation.

It is:

```text
vulnerability detected
→ SEC ID created
→ same issue deduplicated
→ fix verified
→ finding closed
→ vulnerability reintroduced
→ same SEC ID reopened
→ regression recorded
→ policy gate behaves correctly
```

This must work with zero AI providers configured.

Do not progress to AI automation if this deterministic security lifecycle is unreliable.
